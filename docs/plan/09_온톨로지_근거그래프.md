## 0. 원칙과 검사 분담
| 원칙 | 무엇으로 검사하나 |
|---|---|
| ① 발행 문장(Claim)은 근거(Evidence)를 하나 이상 가리킨다 | **SHACL**(구조: 링크가 있는가) |
| ② 문장 속 모든 숫자는 수치 노드(Quantity)의 특정 필드에 묶여 있고, 화면에 그려진 숫자가 그 값·단위와 같다 | 묶임 여부는 **SHACL**, 렌더링된 값의 일치는 **코드**(숫자대조) |
| ③ 가정에서 나온 숫자는 가정에 연결되고 화면에 "가정"으로 표시된다 | 연결은 **SHACL**, 표시는 **렌더러가 강제** |
| ④ 근거는 출처(Dataset)와 공개 시점(availableAt)을 가진다 | **SHACL** |
| ⑤ 판정 문구는 판정 규칙의 결과에서 나온다 | **코드**(판정 문구는 규칙 결과에 묶인 템플릿) |
- SHACL은 **구조·타입·관계**만 검사한다. "근거가 문장 내용을 실제로 뒷받침하는가"는 SHACL이 보장하지 못하므로, 숫자·판정·가정은 코드 검사와 렌더러 규칙으로 막는다. 발표·서식4에서도 이 범위대로 말한다.

## 1. 구성
| 층 | 내용 | 위치 |
|---|---|---|
| 온톨로지(TBox) | 클래스·속성 정의 | `services/knowledge/ontology/crowdcast.ttl` |
| 기준 그래프 | 데이터셋(데이터랩 메뉴·API·파일), 법령 조항, 판정 규칙, 가정, **모델 실행(ModelRun)**. 버전 번호를 가진다 | `ontology/master/*.ttl` + `models/model_card.json` 적재 |
| 세션 그래프 | 예보 1건 = named graph 1개(행사·관측·예보·판정·요인·근거·문장·에이전트 작업). **내용 revision**이 새 사실이 들어올 때마다 증가(문장 상태 전이로는 그대로) | Oxigraph 저장소 `data/app/knowledge/` |
| 형태 규칙 | SHACL shapes | `ontology/shapes/*.ttl` (규칙 하나당 파일 하나) |
| 질의 | SPARQL | `ontology/queries/*.rq` (질의 하나당 파일 하나) |

**검증 범위**: 검증 입력은 항상 **"해당 세션 그래프의 특정 revision + 고정된 기준 그래프 버전 + TBox"**다. 서비스가 이 범위를 한 스냅샷으로 뽑아 검증하므로 다른 세션의 사실이 섞이지 않는다. 검사 결과(Check)에는 revision을 기록하고, 이후 세션이 바뀌면 그 승인은 무효가 된다. 여기서 revision은 **내용 revision**이다 — 새 사실(새 id 또는 새 문장 draft)이 들어올 때만 1 오르고, 문장 상태 전이(draft→candidate·rejected)·발행·같은 내용 재적재로는 오르지 않는다(그래야 게이트 B가 기록한 revision으로 발행할 수 있다). 규칙은 `packages/contracts/rules/integrity.mjs`의 `changesContent`, 단계별 기대값은 `fixtures-integrity/sequences/*.json`의 `revisionAfter`. 한 세션에 대한 쓰기와 검증은 세션 잠금으로 순서를 지킨다.

## 2. 재사용 어휘
| 접두사 | 어휘 | 쓰는 곳 |
|---|---|---|
| `prov:` | W3C PROV-O | 작업(Activity)이 무엇을 쓰고(used) 무엇을 만들었나(wasGeneratedBy), 누가 했나(wasAssociatedWith) |
| `dcat:` `dcterms:` | DCAT, Dublin Core | 데이터셋·제목·발행 기관 |
| `schema:` | schema.org | 행사(Event)·장소(Place) |
| `cito:` | CiTO | 문장 → 근거(`cito:citesAsEvidence`) |
| `cc:` | 인파예보 (`http://crowdcast.local/ont#`) | 아래 클래스·속성 |
- 인스턴스 IRI는 한 이름공간 `id:` = `http://crowdcast.local/id/` 아래 **평면**으로 둔다. 종류는 계약 id의 접두사가 정한다(`packages/contracts/schemas/common.schema.json`, `jsonld/types.json`의 `idRules`).
  - `e-` 행사 · `f-` 예보 · `ev-` 근거 · `c-` 문장 · `q-` 수치 · `obs-` 관측값 · `pr-` 예측 실행 · `mr-` 모델 실행 · `s-` 세션 · `st-` 작업 단계 · `rule-` 규칙 · `law-` 조항 · `as-` 가정 · `ds-` 데이터셋 · `fa-` 요인 · `ck-` 체크리스트
  - 예외 둘: 에이전트는 `agent-<agentId>`(예 `id:agent-explainer` — `rule-check`가 규칙 id와 겹치지 않게), 시군구는 코드 5자리 그대로(`id:28110`).
  - 세션 named graph IRI = 세션 IRI(`id:s-demo-0001`). 검사(Check)·기간·자리표시자는 빈 노드다.
  - 숫자 리터럴: 소수가 나올 수 있는 값(인원 분위수·가정·확률·기여도·좌표)은 `xsd:double`, 개수·순번(임계값·등급·요일·연도·revision)은 `xsd:integer`. `xsd:decimal`은 쓰지 않는다 — JSON-LD 변환이 `0.8`을 `"8.0E-1"^^xsd:decimal`(형식 오류)로 만들어 저장소·SHACL에서 깨진다. 계약 검사가 형식 오류 리터럴 0개를 확인한다.
  - 적재하는 종류: `event`·`forecast`·`claim`·`evidence`·`similar-event`·`region-baseline`(`/facts`). 행사·유사 사례·평시는 타입 스코프 컨텍스트(`Event`·`SimilarCase`·`RegionBaseline`)로 바뀐다. `forecast-report`는 발행된 그래프에서 만드는 결과물이라 적재하지 않는다.
  - 참조 무결성: 적재 전에 `packages/contracts/rules/integrity.mjs`와 같은 판정을 한다 — 문서 안 모든 참조 칸을 **그 문서 + 같은 세션 그래프 + 기준 그래프**에서 찾고(다른 세션은 보지 않는다), 같은 id에 다른 내용이 오면 충돌로 본다. 끊긴 참조·충돌이 있으면 422 + `gate-report`(gate `integrity`)로 거부한다. 기준 id 목록은 `jsonld/master-ids.json`.

## 5. SHACL 규칙 (`ontology/shapes/`)
| ID | 규칙(구조 검사) | 담당 |
|---|---|---|
| S01 | `status`가 `candidate`·`published`인 Claim은 `cito:citesAsEvidence` 1개 이상 | 출처확인 |
| S02 | Claim의 모든 Placeholder는 `quantity`·`field`·`name`을 정확히 1개씩 가진다. 그 Quantity는 `unit`·`timeUnit` 필수 (문장 유형과 관계없이) | 숫자대조 |
| S03 | DataEvidence·Observation은 `derivedFromDataset` 정확히 1개, `availableAt` 정확히 1개(xsd:date) | 출처확인 |
| S04 | Dataset은 `dcterms:title`, `dcterms:publisher`, 그리고 `datalabMenu` 또는 `accessUrl` | 출처확인 |
| S05 | Judgment는 `judgedBy` 1개 이상. 인원 무관 조건으로 대상이면 그중 하나는 LegalRule | 법규담당 |
| S06 | LegalRule은 `basedOnClause` 정확히 1개. RuleEvidence는 `aboutRule` 정확히 1개 | 법규담당 |
| S07 | `peakConcurrent` Quantity는 `dependsOnAssumption` 2개 이상(피크일 계수·동시체류율) | 깐깐이 |
| S08 | Forecast는 `wasGeneratedBy` PredictionRun 정확히 1개, 그 Run은 `used` ModelRun(버전·학습 범위 포함) 정확히 1개와 Observation 1개 이상 | 출처확인 |
| S09 | (SHACL-SPARQL, pySHACL `sh:sparql` 지원) PredictionRun이 쓴 모든 Observation의 `availableAt` ≤ 그 Forecast의 `asOf`, 그리고 Observation이 가리키는 행사 지역이 예보 대상 행사와 맞다 | 깐깐이 |
| S10 | OOD Forecast에 대한 판정·권고 Claim은 "참고용" CheckEvidence를 함께 인용 | 깐깐이 |
| S11 | 모든 Claim은 `wasGeneratedBy` AgentStep → `wasAssociatedWith` TeamAgent | 출처확인 |
| S12 | `status candidate`인 Claim은 근거 Check, (Placeholder가 있으면) 숫자 Check, (`claimType 판정`이면) 규정 Check, (OOD 예보면) 불확실성 Check를 모두 가지고, 그 Check들의 `checksRevision`이 `inSession` 세션의 `revision`과 같고 `passed true` (SHACL-SPARQL) | 팀장 |
- shapes마다 **위반 픽스처**를 둔다. S09는 관측값 누락, 날짜 형식 오류, 미래 공개일, 다른 행사의 관측값 연결을 각각 실패 픽스처로 둔다.
- S08·S09가 기준 그래프(ModelRun)와 세션 그래프를 함께 보므로, §1의 검증 범위 규칙이 필요하다.

## 6. 예시 (Turtle — 파싱·S01~S12 통과 테스트용 정상 그래프의 일부)
계약 픽스처 `fixtures/claim/valid-published.json`을 발행 전(`candidate`) 상태로 옮긴 모양이다. 계약 JSON을 `jsonld/context.jsonld`로 바꾸면 같은 트리플이 나온다(`jsonld/expected/`).
```turtle
@prefix cc:   <http://crowdcast.local/ont#> .
@prefix cito: <http://purl.org/spar/cito/> .
@prefix prov: <http://www.w3.org/ns/prov#> .
@prefix id:   <http://crowdcast.local/id/> .
```

## 7. 설명이 만들어지는 과정과 발행 상태
1. **분석팀**이 도구 결과와 근거 조각(관측값 계보 포함)을 세션 그래프에 넣는다(내용 revision 증가).
2. **게이트 A**(분석 결과 검사: S03·S05·S06·S07·S08·S09)를 통과하면 **숫자 카드**(예측 서비스가 만든 결정적 결과)를 화면에 보낸다. 실패하면 발행을 멈추고 오류 카드를 보낸다.
3. **해설가**는 근거 묶음(근거 id·종류·요약·자리표시자 목록)만 받아 문장을 쓴다 → `status draft`.
4. **게이트 B**: 숫자대조(렌더링 결과 코드 대조)·출처확인(S01·S02·S11)·깐깐이(S10) → 통과한 문장은 `candidate`. 실패한 문장은 1회 재작성, 그래도 실패하면 **재검증된 템플릿 문장**으로 바꾼다.
5. **카드장인·브리핑**은 `candidate` 문장만 골라 배치·요약한다(브리핑은 P0에서 코드 선택, 새 문장을 만들지 않는다).
6. **팀장 발행**: S12를 현재 revision으로 확인한 뒤 `published`로 바꾸고, **그때 처음** 문장과 근거 카드를 SSE로 보낸다.

**상태 전이와 적재 방식** (`packages/contracts/rules/claim-lifecycle.mjs`가 판정, `fixtures-integrity/sequences/`가 실제 순서로 검사)
| 전이 | 어디서 | 조건 |
|---|---|---|
| (없음) → `draft` | `/facts`(schema `claim`) | 새 문장은 draft로만 들어온다 |
| `draft` → `candidate` | `/facts`로 같은 id 재적재 | `rendered`·`checks`(게이트 B 결과, 검사한 revision 포함)만 채운다. 본문·근거·자리표시자·작성 단계는 그대로 |
| `draft`·`candidate` → `rejected` | `/facts`로 같은 id 재적재 | 게이트 B 실패·배치에서 빠짐 |
| `candidate` → `published` | `/publish`만 | 모든 검사 통과, 검사한 revision = 지금 내용 revision(S12), 검증한 revision·masterVersion과 같을 때 |
| 재작성 | 새 id(`c-…-r1`)로 draft부터 | 이전 id는 `rejected`. 같은 id의 본문은 바꾸지 않는다 |
- `published`·`rejected`는 끝 상태다. 같은 내용 재적재(재시도)는 그대로 통과한다.
- **행사·예보·수치·근거·관측값·가정은 세션 안에서 바뀌지 않는다.** 조건을 바꾼 예보(what-if)는 새 예보 id, 행사 정보가 바뀌면 새 세션이다. 같은 id에 다른 내용이 오면 422로 거부한다.

## 9. 화면 표현
- **근거 칩**: 발행 문장 끝의 번호([1][2]) → 근거 카드.
- **근거 카드**(`04` §8): 데이터 / 모델 / 규정 / 사례 / 가정 / 검증.
- **근거 지도**(P1): 문장 → 근거 → 출처 → 데이터셋(React Flow + elkjs).
- **근거 대시보드**(S6): 근거 연결이 없는 발행 문장 수(0이어야 함), SHACL 통과율, **전체 근거 연결률과 데이터랩까지 이어지는 문장 비율을 따로**, 데이터랩 메뉴별 근거 사용 횟수, 규칙별 판정 수.

## 11. 한계
- 온톨로지는 **근거의 구조와 추적**을 위한 것이다. 인원 예측은 모델이, 판정은 규칙이 한다.
- 근거 링크가 있다고 문장이 옳다는 뜻은 아니다. 숫자·판정 일치는 코드 검사가, 예측이 맞았는지는 검증 센터(백테스트·사전 등록 채점)가 보여 준다.
