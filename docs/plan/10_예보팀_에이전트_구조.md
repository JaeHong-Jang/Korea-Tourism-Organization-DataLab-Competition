# 10. 예보팀 — 팀장 1 + 분석·검증·보고 3팀 × 4명

> v4.1 (2026-09-24). 웹 안에서 일하는 AI 에이전트 팀. 구현: `services/gateway/src/team/` (레인 L3). 팀이 함께 쓰는 기억장소는 근거 그래프(`09`), 화면은 `03` F2, 캐릭터는 `04` §7.
> 개발 하네스(Claude 오케스트레이터 + Codex 워커, `AGENTS.md`)와는 별개다. 모양은 같다: 팀장이 일을 나누고, 팀이 하고, 검증을 통과해야 내보낸다.
> v4.1: Codex 교차 리뷰 반영 — 발행 전에는 문장을 화면에 보내지 않음, 보고팀 순서 정리(순환 제거), 새 예보 경로의 LLM 호출 2회로 축소, 시간 목표는 측정 전 가설로 표시.

## 0. 한눈에 보기
```
                         ┌───────────── 팀장 "지휘" ─────────────┐
                         │ 요청 분류 · 작업 배정 · 게이트 · 발행 승인 │
                         └───────┬──────────────┬──────────────┬───┘
            분석팀(파랑)          │   검증팀(청록) │   보고팀(주황)  │
   ┌─────────┬─────────┬────────┴┐ ┌──────┬──────┴┬──────┬──────┐ ┌──────┬──────┬──────┬──────┐
   받아쓰기   동네지기   기록관    예보관  출처확인 숫자대조 법규담당 깐깐이  해설가  카드장인 계획서  브리핑
       └──────────── 모두 같은 근거 그래프(세션 named graph)에 읽고 쓴다 ────────────┘
```
- **LLM을 쓸 수 있는 역할은 5개**(팀장의 요청 분류, 받아쓰기, 해설가, 계획서, 브리핑)이고 나머지 8개는 규칙·모델·그래프 질의다. 실제로는 더 적게 쓴다: **새 예보 한 번에 LLM 호출은 순서대로 2회**(받아쓰기 → 해설가)뿐이다. 첫 메시지는 항상 새 예보라 분류를 건너뛰고, P0 브리핑은 코드가 검증된 문장을 고른다.
- 모든 작업은 `cc:AgentStep`으로 그래프에 남아 "누가 무엇을 보고 이 말을 했는지"를 추적할 수 있다.

## 1. 팀장 — 지휘
| 항목 | 내용 |
|---|---|
| 하는 일 | 요청 분류(새 예보 / 후속 질문 / 초안 / 저장 / 범위 밖) → 플레이북 선택 → 팀원 배정 → 게이트 A·B 확인 → 발행(S12 + `/publish`) |
| LLM | 두 번째 메시지부터 요청 분류 — **키워드 규칙이 한 의도만 가리키면 LLM을 부르지 않고**(결정성·지연), 모호할 때만 스키마 강제 enum 1회, 실패하면 범위 밖 안내(9/25 T-305) |
| 실패 처리 | 분석 결과가 게이트 A를 못 넘으면 **발행 중단 + 오류 카드**(숫자를 추측하지 않는다). 문장이 게이트 B를 못 넘으면 1회 재작성 → 그래도 실패하면 **재검증된 템플릿 문장** |
| 시간 | 요청 전체에 마감(기본 20초, 측정 후 조정). 남은 시간으로 각 호출 예산을 나눈다 |
| 파일 | `team/lead/{classify,playbooks,gates,publish,deadline}.ts` |

## 2. 팀원 12명

|---|---|---|---|---|---|---|---|

## 3. 일하는 순서 (새 예보 플레이북)
| 단계 | 누가 | 병렬 | 화면에 보내는 것 |
|---|---|---|---|
| 0 접수 | 팀장(첫 메시지는 분류 생략) | — | 펫 상태만 |
| 1 분석 | 받아쓰기 → (동네지기 ∥ 기록관) → 예보관 | 동네지기·기록관 | 행사 카드, 되묻기 |
| 게이트 A | 출처확인(S03·S04·S08) ∥ 법규담당(S05·S06) ∥ 깐깐이(S07·S09) | 병렬 | 통과 시 **숫자 카드·판정 배너**(예측 서비스의 결정적 결과) / 실패 시 오류 카드 |
| 2 해설 | 해설가 | — | 펫 상태만(문장은 아직 보내지 않음) |
| 게이트 B | 숫자대조(S02 + 렌더 대조) ∥ 출처확인(S01·S11) ∥ 깐깐이(S10) ∥ 법규담당(판정 문구) | 병렬 | 펫 상태만 |
| 3 배치·요약 | 카드장인 ∥ 브리핑(코드) | 병렬 | — |
| 4 발행 | 팀장(S12 → `/publish`) | — | **이때 처음** 설명 문장·근거 칩·근거 카드·요약·다음 할 일 |
- **시간 목표(측정 전 가설)**: 숫자 카드까지 5초, 발행까지 15초(모델이 이미 올라온 상태, 로컬 4b). T-302·T-304에서 **모델 첫 로딩 / 이미 로딩됨**, **재시도 포함 / 미포함**을 나눠 전체 경로의 p50·p95를 재고 확정한다. 출력 토큰 상한을 두고, 3D 장면과 LLM이 같은 GPU를 쓰는 조건에서도 잰다.

**다른 플레이북** (모두 마지막은 게이트 B → 발행)
| 요청 | 움직이는 팀원 |
|---|---|
| "왜 이렇게 많아?" | 해설가(요인 근거) → 게이트 B → 발행 |
| "계획 초안 만들어 줘" | 계획서 → 게이트 B(섹션별) → 발행 → records 저장 |
| "저장해 줘" | 팀장 → records(발행된 예보만) |
| "비 오면? / 일요일이면?"(P1) | 예보관(`/whatif`) → 게이트 A → 해설가 → 게이트 B → 발행 |
| 범위 밖 질문 | 팀장이 정중히 범위를 안내(템플릿) |

## 4. SSE 이벤트 (계약 `packages/contracts/sse-events.md`)
`agent_status`(agent·team·state[idle·working·waiting·done·blocked]·note) · `event_card` · `ask` · `forecast`(게이트 A 통과 후) · `claim`·`evidence`(발행 후에만) · `gate`(A/B·passed·violations 요약) · `suggest` · `done` · `error`
- 작업판은 `agent_status`·`gate`만으로 펫을 그린다. 예보서는 `forecast`와 **발행된** `claim`·`evidence`만으로 그린다.

## 5. 예보팀 작업판 (화면, `03` S2)
- 팀장 1 + 팀별 한 줄(4명씩). 일하는 펫은 움직이고, 말풍선에 짧은 메모("인천 중구로 찾았어요", "숫자 3개 확인했어요").
- 펫을 누르면 그 팀원의 작업 기록(입력 요약·출력 근거·걸린 시간).
- 게이트를 통과하면 팀장이 도장을 찍는다. 위반이 있으면 해당 검증팀원이 손을 들고 위반 요약을 보여 준다.
- 화면 문구는 "예보팀이 확인했어요"처럼 팀의 말투. 발표·도움말에는 "AI 에이전트 12 + 팀장"이라고 분명히 밝힌다.

## 6. 규칙 기반과 LLM의 경계
| 일 | 누가 | 이유 |
|---|---|---|
| 인원 예측·환산·판정 | 예측 서비스(모델·규칙) | 재현·검증 가능 |
| 근거 구조 검사 | 근거 그래프(SHACL) | 기계 검사 |
| 숫자·판정 문구 일치 | 게이트웨이 코드(숫자대조·법규담당) | SHACL이 못 보는 내용 대조 |
| 필드 추출·요청 분류 | LLM(스키마 강제) | 자연어 이해 |
| 설명·초안 문장 | LLM(근거 묶음·자리표시자) — 설명의 요인 문장은 라벨 그대로(검증 가능한 것만), 계획서 섹션은 T-306 | 글쓰기, 숫자는 코드가 채움 |
| 발행 | 팀장(S12 + 원자적 발행) | 검증 안 된 문장은 나가지 않음 |

## 7. 테스트
- 팀원마다 단위테스트(가짜 LLM·가짜 서비스), 플레이북마다 시나리오 테스트, 게이트는 위반 픽스처로 막히는지.
- **발행 전 문장이 SSE로 나가지 않는지** 이벤트 순서 테스트.
- C 평가(`05` §4-4): 시나리오 20개 — 근거 연결 없는 발행 0, 숫자 불일치 0, 되묻기 적중, 전체 경로 p50·p95.
