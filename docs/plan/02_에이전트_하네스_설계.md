# AI 에이전트 · 하네스 설계 — "어떻게, 어디까지 자동으로"

> 2026-08-18 v1. `01_행사인파예보_에이전트_계획.md`의 3절을 체계화한 문서.
> 원칙 3개: **① 계산은 코드가, 판단·설명·문서는 LLM이 ② 모든 LLM 행동은 도구 호출로만 세계에 닿는다 ③ 하네스가 검증·기록·중단을 책임진다.**

---

## 0. 에이전트는 셋이다
| 에이전트 | 언제 도나 | 하는 일 | 트리거 |
|---|---|---|---|
| **A. 예보 에이전트** (사용자용) | 웹에서 사용자가 말할 때 | 행사 구조화 → 조회 → 예측 → 근거 → 계획 초안 → 알림 | 채팅 |
| **B. 분석 자동화 에이전트** (오프라인) | 매주 1회 + 데이터 갱신 시 | 데이터 수집 → 라벨 재구축 → 학습 → 백테스트 → 리포트·대시보드 갱신 → 이상 시 알림 | 스케줄(cron)/수동 |
| **C. 평가 에이전트** (품질 게이트) | A·B의 결과가 나올 때마다 | 골든 케이스 재현, 도구 회귀 테스트, 설명 품질 채점, 배포 승인/차단 | CI·B 완료 후 |

세 에이전트가 **같은 하네스**(도구 레지스트리·상태·트레이스·가드레일) 위에서 돈다.

## 1. 하네스 구성요소 (공통)
```
┌─ Orchestrator (루프) ────────────────────────────────────────┐
│  plan → act(tool) → observe → reflect → (loop | stop)          │
│  · 최대 스텝/토큰/시간 예산   · 재시도·백오프   · 중단 조건       │
├─ Tool Registry ─────────────────────────────────────────────┤
│  JSON Schema 입출력 · 결정적 함수 · 타임아웃 · 캐시 · 권한 등급    │
├─ State / Memory ────────────────────────────────────────────┤
│  session(대화·행사 구조체) · run(B의 실행 아티팩트) · kb(유사행사·매뉴얼)│
├─ Guardrails ────────────────────────────────────────────────┤
│  스키마 검증 · 수치 범위 · OOD 판정 · 금칙(단정·법적 조언) · 워터마크 │
├─ Evals ─────────────────────────────────────────────────────┤
│  골든셋 · 도구 단위테스트 · 지표 임계치 · LLM-judge · 회귀 비교      │
├─ Observability ─────────────────────────────────────────────┤
│  trace(스텝·도구·지연·토큰·비용) · 아티팩트 저장 · 데모용 로그 재생   │
└──────────────────────────────────────────────────────────────┘
```
구현: Python 패키지 `src/agent/` (`harness/`: loop, registry, state, guard, trace / `tools/` / `prompts/` / `evals/`). LLM = Claude API tool use, 스트리밍. 프레임워크 없이 얇게(디버깅·발표 설명이 쉬움).

## 2. A. 예보 에이전트 — 사용자용
### 2-1. 루프
```
입력(사용자 발화) 
→ [Planner] 어떤 도구가 필요한지 결정 (system prompt의 절차 + 현재 state)
→ [Act] 도구 호출 (독립 도구는 병렬)
→ [Observe] 결과를 state에 병합, 스키마·범위 검증 실패 시 재시도(≤2) 또는 사용자에게 질문
→ [Reflect] 필수 필드 충족? 예측 완료? 계획 초안 요청됨? → 다음 스텝 or 종료
정지 조건: 사용자 요청 충족 / 스텝 8 초과 / 토큰 예산 초과 / 가드 위반
```
### 2-2. 상태 (state.event)
```json
{ "name":"", "type":"불꽃|음악|먹거리|꽃|전통|스포츠|기타", "start":"YYYY-MM-DD","end":"",
  "time_of_day":"주간|야간|종일", "sido":"","sigungu_code":"", "venue":"", "lat":0,"lng":0,
  "budget_krw":null, "fee":"무료|유료|미상", "host_type":"지자체|민간|대학|기타",
  "edition":null, "promo":["인스타","유튜브","현수막"], "expected_by_host":null,
  "missing":["budget_krw"], "prediction":null, "plan_draft":null }
```
### 2-3. 도구 스펙 (요약; 전체 스키마는 `src/agent/tools/*.json`)
| 도구 | in → out | 결정성 | 캐시 |
|---|---|---|---|
| `parse_event(text)` | 자유문 → event 부분 채움 + missing | LLM 보조(구조화 전용 프롬프트) | – |
| `geocode_region(venue)` | 장소명 → sido/sigungu_code/좌표 | 결정적(행정구역 사전 + TourAPI 검색) | 영구 |
| `region_baseline(sigungu, start, end)` | 데이터랩 API 15101972 → 평시 일방문자·요일 배수·전년 동기 | 결정적 | 24h |
| `find_similar_events(event, k)` | 라벨 테이블에서 유형·시도·예산대·월 유사도 top-k | 결정적 | – |
| `predict_attendance(event)` | LightGBM → p10/p50/p90, P(≥1000), SHAP top5, OOD 플래그 | 결정적 | – |
| `draft_safety_plan(event, prediction)` | 매뉴얼 항목 템플릿 채움 | LLM 생성 + 템플릿 검증 | – |
| `schedule_recheck(event_id, days_before)` | 알림 등록 | 결정적 | – |
| `save_feedback(event_id, actual, note)` | 사후 실제 인원 저장(→ B의 학습 데이터) | 결정적 | – |

### 2-4. 프롬프트 구조 (system)
1. 역할·목적 (안전관리계획 판정 보조, 참고용) 2. 절차(위 루프를 문장으로) 3. 도구 사용 규칙(숫자는 반드시 도구 결과 인용, 없는 값 추정 금지) 4. 출력 형식(근거 카드 3개·구간·확률·다음 행동 제안) 5. 금칙(단정, 법적 조언, 구간 밖 수치) 6. 예시 2개(성공/되묻기).

### 2-5. 가드레일
- 스키마: 도구 입출력 pydantic 검증 실패 → 자동 재시도 1회 → 사용자에게 명시.
- 수치: p50이 개최지 평시 방문자의 50배 초과 or OOD 플래그 → "유사 사례 부족, 참고만" 배지 + 계획 초안 비활성.
- 문장: 정규식으로 "확실히/반드시 ~명" 단정 표현 차단, 계획 초안엔 "담당자 검토 필수" 고정 문구.
- 사용자 개인정보 저장 안 함(행사 정보만).

## 3. B. 분석 자동화 에이전트 — 하네스 엔지니어링의 핵심
"분석을 자동으로" = **DAG는 코드가 고정**하고, 에이전트는 **각 단계의 판단(파라미터·이상 여부·해석)과 리포트 작성**을 맡는다. 계산 결과는 항상 결정적으로 재현 가능.

### 3-1. 파이프라인 DAG (`src/pipeline/`)
```
fetch_visitors  ─┐
fetch_festivals ─┼→ build_labels → build_features → train → backtest → publish
fetch_datalab   ─┘        │              │            │         │          │
 (수동 CSV 감시)         QC gate        QC gate      gate     gate      dashboard/report
```
| 단계 | 코드(결정적) | 에이전트 판단 | 게이트(자동 검증) |
|---|---|---|---|
| fetch_visitors | API 15101972 증분 수집(시군구×일), 캐시 | 결측·급락 구간 원인 추정(갱신 지연 vs 실제) | 결측률<2%, 최신일 ≥ 오늘−7 |
| fetch_festivals | 문체부 xlsx, 데이터랩 축제 CSV(수동 투입 폴더 감시), TourAPI searchFestival2 | 신규 파일 스키마 변화 감지·매핑 제안 | 필수 컬럼 존재, 중복 제거 |
| build_labels | 골드(데이터랩 축제 방문자) + 실버(기간 순증 = 기간 방문 − 전후 4주 동요일 baseline) | baseline 윈도(±2/4/6주) 중 잔차 최소안 선택 근거 기록, 이상 라벨(음수·극단) 격리 | 라벨 N≥150, 음수 비율<5% |
| build_features | 유형·기간·예산·요일·계절·시도·회차·평시 방문·TMAP | 피처 누수 점검(개최 이후 정보 사용 여부) | 누수 체크 통과 |
| train | LightGBM 회귀(log)+quantile+분류, 고정 seed | 하이퍼파라미터 탐색 범위 내 선택, 과적합 징후 해석 | 학습 완료·아티팩트 저장 |
| backtest | leave-one-year-out, 유형별 MAPE·F1·캘리브레이션, 골든 케이스 재현 | **결과 해석·전 주 대비 변화 원인·리포트 초안** | MAPE ≤ 직전+3%p, F1 ≥ 직전−0.03, 골든 재현 통과 |
| publish | 모델 pkl 승격, P4 대시보드 데이터, `reports/backtest_YYYYMMDD.md` | 리포트 서술·차트 캡션 | C 에이전트 승인 |

### 3-2. 실행 방식
- 스케줄: 매주 월 06:00(cron/GitHub Actions) + 수동 `make pipeline`.
- 에이전트 호출 지점: 각 단계 후 `observe(artifacts) → judge → decide(continue|retry|halt|notify)`. 게이트 실패 시 자동 재시도(파라미터 조정 1회) → 그래도 실패면 **halt + Slack/카톡 알림 + 원인 리포트**.
- 산출물 규약: `runs/{run_id}/` 아래 단계별 입력 해시·출력·로그·에이전트 판단 JSON → 어떤 리포트 숫자도 run_id로 재현.
- 비용 상한: 런당 LLM 호출 ≤ 20, 토큰 ≤ 200k.

### 3-3. 자동 생성 리포트 (`reports/backtest_*.md`) 고정 목차
1. 데이터 현황(라벨 N, 기간) 2. 전체·유형별 MAPE/F1 표 3. 예측 vs 실제 산점도 4. 골든 케이스(영종·약사사…) 재현표 5. 전 주 대비 변화와 원인(에이전트 서술) 6. 한계·다음 액션. → 서식4 4)성과와 P4 대시보드에 그대로 사용.

## 4. C. 평가 에이전트 — 품질 게이트
| 평가 | 대상 | 방법 | 통과 기준 |
|---|---|---|---|
| 골든셋 | 모델 | 언론 실제 인원 확보 사례 10~20건(영종 3만, 약사사 1,500 등) D-14 정보만으로 예측 | 구간 내 포함 ≥ 70%, 1,000명 판정 정확 100% |
| 도구 회귀 | A 도구 8개 | pytest 고정 입력→출력 스냅샷 | 전부 통과 |
| 대화 시나리오 | A | 시나리오 20개(정상·누락 정보·OOD·악의 입력) 자동 실행 | 필수 되묻기 발생, 금칙 0건, 스텝 ≤ 8 |
| 설명 품질 | A 근거 문장 | LLM-judge 루브릭(도구 수치 인용 여부·과장 없음·유사사례 언급) 1~5 | 평균 ≥ 4.0 |
| 계획 초안 | `draft_safety_plan` | 매뉴얼 필수 항목 커버리지 체크리스트 | 100% |
| 성능 회귀 | B 결과 | 직전 run 대비 | 3-1 게이트 |
실행: CI(PR마다 도구·시나리오), B 완료 후(골든·성능), 배포 전 수동 1회.

## 5. 관측·데모
- 트레이스: 세션별 `traces/{session_id}.jsonl` — 스텝, 도구명, 입력 요약, 출력 요약, 지연, 토큰, 가드 이벤트. P2 우측 "에이전트 로그" 패널이 이걸 실시간으로 그림 → 심사위원이 데이터랩 호출을 눈으로 확인.
- 데모 재생: 저장된 트레이스를 재생하는 모드(네트워크 장애 대비).
- 지표: 세션당 평균 스텝·도구 호출·응답 시간(목표 < 30초), 되묻기 비율, 계획 초안 채택률.

## 6. 구현 순서 (일정과의 매핑)
| 주 | 하네스 작업 |
|---|---|
| 1 | `harness/registry.py`(스키마·타임아웃·캐시), `trace.py`, 도구 3개(`geocode`,`region_baseline`,`find_similar` 더미) · 파이프라인 fetch 단계 + QC 게이트 |
| 2 | `predict_attendance` 연결, build_labels/train/backtest 단계 + 게이트, 첫 자동 리포트 |
| 3 | A 루프·프롬프트·가드레일, SSE 스트리밍, `parse_event` |
| 4 | `draft_safety_plan`, C 골든셋·시나리오·LLM-judge, CI |
| 5 | B 스케줄러·알림, 재학습(`save_feedback` 반영), 데모 재생 모드 |
| 6 | 리포트 → 서식4, 트레이스 캡처 → 참고자료 |

## 7. 발표에서 이 설계를 어떻게 말하나 (창의·데이터·전달력)
- "예측은 모델, 판단·문서는 에이전트, 검증은 하네스" 한 장 다이어그램.
- 라이브: 심사위원 행사 입력 → 로그 패널에 데이터랩 API 호출·유사행사·SHAP 흐름 → 계획 초안.
- 자동 분석: "매주 월요일 스스로 데이터를 받아 재학습·백테스트하고 리포트를 씁니다 — 이 숫자(MAPE·F1)는 지난 월요일 run_id ___에서 나왔습니다."
