[High → 오케스트레이터 판정: 계획 정본에 따라 **제외하지 않는다**] 리뷰는 TourAPI 일정의 `date_available_at > asOf`를 공개 시점 위반으로 봤지만, 06 §3(9/25 개정·계획 리뷰 PASS)은 **행사 속성(일정 포함)은 예보 요청의 입력**이고 D-14 공개 시점 규칙은 외부 관측에만 건다. 대신 투명하게: 요약 parquet·QC에 `date_source`·`date_available_at`을 싣고, QC에 "일정 공개일이 asOf 뒤인 행사 N건(입력으로 사용 — 06 §3)"을 적는다. 사전 등록(T-207)은 자기 규칙(`date_available_at ≤ 등록일`)으로 거른다. 테스트: 그런 행사도 예보되고 QC에 집계된다.

## 게이트 피드백 2회차 (게이트 3 sol FAIL — High 1·Med 1, 오케스트레이터 판정 포함) — 워크트리에 1회차 결과가 있다
오케스트레이터 게이트 2: forecast 전체 1158·ruff check 통과. 1회차 지적 세 항목 중 공개일 기록·X-Run-Id는 해결, 교체는 부분 해결(리뷰 판정).
1. [High → 오케스트레이터 판정: **동시 실행만 막는다**] 리뷰는 세 `os.replace` 사이에 프로세스가 죽으면 runId가 섞인다고 봤다. 이것은 1회차 판정의 설계("세 파일 같은 runId + 읽는 쪽이 다르면 거부, 다음 정상 실행이 바로잡는다")로 **감지**하는 것으로 충분하다 — 원자적 완료 표식은 만들지 않는다. 대신 두 배치가 동시에 발행하는 경우는 막는다: `run_batch` 전체를 배타 잠금(`paths.PROCESSED / ".upcoming.lock"`, `fcntl.flock` LOCK_EX|LOCK_NB — `models/publish.py`의 `run_lock`과 같은 방식, 잠겨 있으면 "다른 일괄 예보 실행 중" 오류)으로 감싼다. QC 머리에 "중단 시 세 파일 runId가 다를 수 있음 — 읽는 쪽이 거부" 한 줄. 테스트: 잠금 잡힌 상태에서 두 번째 실행 → 오류·산출물 그대로.
2. [Med] `run_identifier`가 승격 포인터 전체(`promotedAt` 포함)를 해시 → 같은 입력·모델을 다시 승격만 해도 runId·산출물 바이트가 바뀐다. 포인터에서 `modelVersion`·백테스트 `runId`·`verdict`만 해시한다. 테스트: `promotedAt`만 다른 포인터 → 같은 runId.
- 확인: `pytest -q services/forecast/tests`(전체), `ruff check`. 실제 실행은 하지 않는다(T-204b 뒤 다시 돌린다).
