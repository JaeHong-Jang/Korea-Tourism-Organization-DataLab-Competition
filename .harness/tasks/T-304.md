## 게이트 피드백 1회차 (워커 BLOCKED → 오케스트레이터 결정) — 워크트리에 결과가 있다
1회차: 구현 없이 차단 사유만 기록(기존 744 통과). 막힌 세 가지를 이렇게 정한다 — 계약 변경 없이 간다.
1. **모델 상태 문장에는 숫자를 쓰지 않는다**: `modelVerdict=미검증`이면 "사례 재현 검증 전 임시 사용 모델로 만든 예보예요 — 참고용으로 봐 주세요"(숫자 0개, 모델 근거 인용). 06 §8의 "골든 사례 0건 — …" 문구는 **화면이 `predictionRun.modelVerdict`로 직접 표시**한다(T-406) — 문장(claim)이 아니다. `건` 단위는 필요 없다.
2. **규칙 상수**: 판정·권고 문장에 나오는 법정 기준 숫자(예: "순간 최대 1,000명", "5,000명")는 Quantity가 아니라 **규칙의 문구**다 → 숫자대조는 "자리표시자에 묶인 Quantity 값" **또는** "그 문장이 `evidenceIds`로 인용한 RuleEvidence·조항 근거의 문구에 같은 숫자·단위가 그대로 있는 경우"만 허용한다(그 밖의 숫자는 여전히 위반). 판정 문장은 판정 규칙 템플릿 문구 그대로라 이 규칙으로 통과한다. 테스트: 인용 안 한 규칙의 숫자 → 위반, 인용한 규칙 문구의 숫자 → 통과, 규칙 문구와 다른 숫자(1,500명) → 위반.
3. **확률 문장은 이번 범위 밖**: 지금 사용 모델은 G0에 따라 `basis=구간`이라 확률 %를 쓰지 않는다(06 §6). `basis=확률`일 때의 확률 문장은 `probabilities`를 Quantity로 싣는 계약이 필요하므로 **만들지 않고** 리포트에 CONTRACT-CHANGE 후속으로만 적는다(템플릿은 `basis=확률`이면 수치 문장에서 확률 자리를 빼고 구간만).
4. **허용 경로 추가**: `services/gateway/src/team/runtime/{events,run-request,sessions}.ts` — 새 플레이북 단계를 잇는 **최소 수정만**(이벤트 이름·순서 규칙·세션 상태 필드). 다른 런타임 동작은 바꾸지 않는다.
- 나머지는 명세 본문 그대로(해설가·템플릿·검증팀·게이트 B·카드장인·브리핑·발행·스냅샷·실사용 확인).

## 게이트 피드백 2회차 (오케스트레이터 실사용 확인 — 발행 중단·LLM 미사용) — 워크트리에 1회차 결과가 있다
오케스트레이터가 develop의 forecast(b2b23e5 포함)·knowledge·records와 워크트리 게이트웨이로 상담을 돌렸다(소래포구 10/2 먹거리 축제). 구현 경로(게이트 A → 해설 → 검증팀 → 게이트 B → 카드장인·브리핑 → 발행 → 스냅샷)와 "발행 전 claim·evidence 0"(첫 claim seq 42, publish 게이트 뒤)은 맞다. 아래 네 가지 때문에 실제 서비스에서는 **발행이 막히거나 LLM이 한 번도 쓰이지 않는다**. 실제 예보 응답: `data/cache/t304/forecast-live-sorae.json`(OOD·`basis=구간`·근거 20개 — 픽스처로 복사해 쓴다).
1. [High] **해설가 입력이 컨텍스트를 넘는다** — `explanationInput`이 19,252자 = 11,906토큰, Ollama(`qwen3:4b-instruct-2507-q4_K_M`, `n_ctx` 4096)가 400 `exceed_context_size_error` → 매번 템플릿(41ms). 고칠 것:
   - 고정 문장(판정·권고·모델 상태·참고용)은 **LLM에 맡기지 않고** 게이트웨이가 템플릿에서 그대로 넣는다(규칙 문구 그대로라 LLM이 베낄 이유가 없다). LLM은 수치·요인·설명 문장만 **최대 3개** 쓴다.
   - 입력 압축: quantities(id·name·unit·p10/p50/p90/value), factors 상위 3(name·direction·evidenceIds), evidence는 **id·kind·title만**(summary 원문 제외), judgment는 level·label·basis·ruleIds, violations. 테스트: 실제 예보 픽스처로 `explanationInput(...)` ≤ 4,000자.
   - 실패 사유를 삼키지 않는다: 원문 없이 분류 코드(`context`·`timeout`·`schema`·`http`·`parse`)를 agent_step `note`에 남긴다("템플릿 설명을 검증팀에 넘겨요(timeout)" 식).

[High] **S10 참고용 근거 모양 불일치** — forecast의 check 근거는 `kind=check`, `checkResult={checkKind:"ood", passed:true, revision:0}`, **`title`="참고용 — 담당자 검토 필수"**, `summary`=사유 JSON(`{"reasons":[…]}`)이다. `reviewEvidence`가 `summary.includes(REVIEW_NOTICE)`를 요구해 0건 → 템플릿이 인용 못 함 → 게이트 B S10×6·S01(근거 0개 참고용 문장) → `SERVICE_UNAVAILABLE` 발행 중단. `title === REVIEW_NOTICE`로 바꾸고 테스트 픽스처를 실제 모양으로(오케스트레이터가 이 한 줄만 바꿔 돌려 보니 템플릿 경로 발행까지 완결됐다 — 되돌려 둠).

## 오케스트레이터 판정·수정 2 (재리뷰 sol FAIL — High 3·Med 1)
리뷰가 맞다: 풀어 쓴 요인 문장은 규칙으로 뜻(다른 요인 내용)·부정("늘지 않아요")·한글 수사("천 명")를 검증할 수 없다 → **"검증된 문장만 발행" 원칙에 따라 요인 문장은 예측 서비스의 라벨 그대로만 발행**한다. 앞의 완화(사람 수·방향 표현)는 되돌렸다.
- 법규담당: 요인 = 라벨 그대로 + 그 요인 근거 전부 인용(워커 원래 설계).
- 해설가: LLM 출력은 요인 수와 같은 개수, 요인 순서대로, 각 문장 = 그 요인 라벨 그대로·그 요인 근거만 인용일 때만 받는다(아니면 `schema` → 템플릿). 프롬프트는 "name을 글자 그대로 옮기세요". Ollama 스키마 min=max=요인 수.
- 결과적으로 발행 요인 문장은 LLM 경로·템플릿 경로 모두 결정적 라벨과 같다. LLM 호출은 근거 선택·형식 검증 경로를 유지하는 역할로 남는다(더 큰 모델·검증기가 생기면 풀어 쓰기를 다시 검토 — backlog).
- 테스트: 풀어 쓴 문장 다섯 가지(방향 맞는 문장·부정·한글 수사·다른 요인 내용·사람 아님) 모두 발행 안 함, 게이트 B 두 번 실패 뒤 템플릿 발행(해설가 결과 훼손 방식). 821 통과. 실사용(fake + 실제 Ollama): 해설 LLM 0.84초, "토요일 저녁 개최라 늘어요" 발행.
