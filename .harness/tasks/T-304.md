- 인터페이스(10 §3 새 예보 플레이북 그대로):
  - **해설가(LLM 1회)**: 입력 = 게이트 A를 지난 예보의 근거 묶음(`evidence`·`judgment`·`factors`·수치 Quantity 목록) → `claim[]`(status `draft`). 문장 **안의 숫자는 모두 자리표시자** `{{name}}`이고 `placeholders[]`가 Quantity id·필드에 묶인다, 문장마다 `evidenceIds` 1개 이상, `generatedBy`는 해설가·모델명. Ollama 스키마 강제 JSON, 예산은 요청 마감에서 나눈다. 실패·시간 초과·스키마 위반 → **템플릿**.
  - **템플릿(`templates.ts`)**: LLM 없이 같은 모양의 문장을 만든다 — 판정(판정 규칙 결과 문구 그대로), 수치(순간 최대 `{{peak_p10}}~{{peak_p90}}명` 추정 — `basis=구간`이면 확률 % 없이 "표본 한계로 구간 기준 표시", `basis=확률`이면 1,000명 이상 확률 자리표시자), 요인(요인이 있을 때만, 상위 3개, 각 요인의 근거 id), 권고(체크리스트 항목), **모델 상태**(`predictionRun.modelVerdict=미검증`이면 "골든 사례 0건 — 사례 재현 검증 전 임시 사용" + 모델 근거). 템플릿은 테스트에서 게이트 B를 통과하는 것으로 **미리 검증**한다.
  - **문장 적재와 상태 전이**: draft 적재 → 검사(아래) → 같은 id로 `candidate` + `checks[].revision` = 그 내용 revision으로 재적재(`claim-lifecycle.mjs` 규칙 — 상태 전이는 revision을 올리지 않는다).
  - **검증팀(게이트웨이 코드 + knowledge)**: 숫자대조 = 자리표시자를 Quantity 값으로 채운 `rendered`의 **모든 숫자·단위가 Quantity와 일치**(자리표시자 밖 숫자 0개) + S02, 법규담당 = 판정 문장이 판정 규칙 템플릿과 같고 법정/자체 구분이 맞는지, 깐깐이 = OOD면 "참고용 — 담당자 검토 필수" 인용(S10)·`basis=구간`이면 % 0개, 출처확인 = S01·S11(knowledge). 코드 검사 결과는 `checks[]`로 싣고, knowledge `/validate`를 게이트 B 규칙 목록으로(현재 revision·masterVersion 고정) 부른다.
  - **게이트 B 실패**: 1회 재작성(해설가 — 위반 요약을 입력에 붙여) → 또 실패하면 템플릿 → 템플릿도 실패하면 발행 중단(`error` SERVICE_UNAVAILABLE "설명 문장을 검증하지 못했어요", `done.forecastId=null` — 숫자 카드는 이미 나갔다). 게이트 B 재검사 규칙은 sse-events R4·R10 그대로.
  - **카드장인(규칙)**: candidate 문장의 근거를 어떤 카드(근거 종류별)로 어떤 순서로 보일지 → 예보서 `forecast-report`의 배치. **브리핑(P0 코드)**: 검증된 문장 중에서 세 줄 요약·다음 할 일(`suggest.actions`)을 **고른다**(새 문장을 만들지 않는다).
  - **발행(팀장)**: knowledge `/publish`(S12, 게이트 B의 revision·masterVersion) 성공 → 그때 처음 SSE `claim`×N(status `published`)·`evidence`{items}·`suggest`·`done`{forecastId = 카드 id}. 발행 뒤 records `POST /v1/events/{id}/snapshots`에 `forecast-report` 저장(실패하면 로그 + `suggest`에 "예보서 링크를 만들지 못했어요" — 발행은 되돌리지 않는다).
  - 요청 마감(기본 20초)은 T-303 방식 그대로 — 남은 시간이 해설 예산보다 적으면 바로 템플릿.

## 게이트 피드백 1회차 (워커 BLOCKED → 오케스트레이터 결정) — 워크트리에 결과가 있다
1회차: 구현 없이 차단 사유만 기록(기존 744 통과). 막힌 세 가지를 이렇게 정한다 — 계약 변경 없이 간다.
1. **모델 상태 문장에는 숫자를 쓰지 않는다**: `modelVerdict=미검증`이면 "사례 재현 검증 전 임시 사용 모델로 만든 예보예요 — 참고용으로 봐 주세요"(숫자 0개, 모델 근거 인용). 06 §8의 "골든 사례 0건 — …" 문구는 **화면이 `predictionRun.modelVerdict`로 직접 표시**한다(T-406) — 문장(claim)이 아니다. `건` 단위는 필요 없다.
2. **규칙 상수**: 판정·권고 문장에 나오는 법정 기준 숫자(예: "순간 최대 1,000명", "5,000명")는 Quantity가 아니라 **규칙의 문구**다 → 숫자대조는 "자리표시자에 묶인 Quantity 값" **또는** "그 문장이 `evidenceIds`로 인용한 RuleEvidence·조항 근거의 문구에 같은 숫자·단위가 그대로 있는 경우"만 허용한다(그 밖의 숫자는 여전히 위반). 판정 문장은 판정 규칙 템플릿 문구 그대로라 이 규칙으로 통과한다. 테스트: 인용 안 한 규칙의 숫자 → 위반, 인용한 규칙 문구의 숫자 → 통과, 규칙 문구와 다른 숫자(1,500명) → 위반.
3. **확률 문장은 이번 범위 밖**: 지금 사용 모델은 G0에 따라 `basis=구간`이라 확률 %를 쓰지 않는다(06 §6). `basis=확률`일 때의 확률 문장은 `probabilities`를 Quantity로 싣는 계약이 필요하므로 **만들지 않고** 리포트에 CONTRACT-CHANGE 후속으로만 적는다(템플릿은 `basis=확률`이면 수치 문장에서 확률 자리를 빼고 구간만).
4. **허용 경로 추가**: `services/gateway/src/team/runtime/{events,run-request,sessions}.ts` — 새 플레이북 단계를 잇는 **최소 수정만**(이벤트 이름·순서 규칙·세션 상태 필드). 다른 런타임 동작은 바꾸지 않는다.
