- 인터페이스:
  - **규칙**(`rules.py` 상수 = `RULES.md` 내용, 둘이 다르면 테스트 실패): 등록일 2026-09-29(KST). 대상 = T-205 요약 중 ① 시작일 ≥ 등록일 + 3일, ② 종료일 ≤ 2026-10-31(채점 자료가 11월 안에 나오도록), ③ 시군구 확정·연속성 끊김 아님, ④ `date_available_at`(TourAPI 일정이면) ≤ 등록일, ⑤ 실버 신호를 잡을 수 있는 곳(개최지 평시 기준선 표본 ≥ 3일·기간 ≤ 14일 — T-103 조건과 같게). 등급 1~4 **층화**: 등급별로 행사 id 해시(sha256(eventId + "2026-09-29")) 오름차순으로 뽑아 등급당 최대 8건, 총 20건 이상이 되도록(모자라면 있는 만큼 + 사유). 취소·연기 확인된 행사는 제외(기록)
  - `POST /v1/preregistration/select` → 선정 목록(`festival-summary[]`, 규칙 순서 그대로 — 결정적)
  - `python -m crowdcast.scoring register --dry-run`(기본): records `POST /v1/ledger` 본문(`{forecastId, eventId, leadDays, forecast:{dailyMeanP10,P50,P90,level}}`)을 만들어 `paths.PROCESSED/prereg_payloads.json`에 쓰고 **보내지 않는다**. `--send`는 오케스트레이터가 9/29에만 쓴다(테스트는 가짜 records로). leadDays = 시작일 − 등록일
  - `score`(`GET /v1/preregistration/scores`): 원장(`GET /v1/ledger`) 항목마다 실측 = T-103 실버와 **같은 함수·같은 정의**(행사 전 기준선) — `region_daily`에 행사 기간이 다 들어왔으면 계산, 아니면 `대기`. 신호 미검출(3σ 미만)은 `채점 불가`(분모에서 빼고 건수 공개), 취소는 `취소`. `inInterval` = p10 ≤ 실측 ≤ p90, `levelMatch` = 실측을 같은 환산으로 등급화해 비교. 응답 = 계약 `preregistration-scores`(`tag`·`rulesDoc` = `RULES.md` 경로)
