- 인터페이스:
  - 순서: records `GET /v1/events/{id}`(없으면 404) → 직전 스냅샷 `GET /v1/events/{id}/snapshots`의 최신(없으면 null) → 저장된 행사 입력으로 예보관(`/v1/predict`) → 게이트 A → 보고팀(체크리스트·설명 — LLM 호출 상한은 상담과 같게: 보통 2, 고쳐 쓰기 포함 최대 3) → 게이트 B(근거·숫자 검산) → knowledge 발행 → records `POST /v1/events/{id}/snapshots`. **어느 게이트든 실패하면 발행·저장하지 않고 409**(code·message에 이유 — 어떤 게이트인지).
  - 세션: 내부 세션 id를 새로 만들어 knowledge facts·발행에 쓴다(상담 세션과 섞이지 않게, id 접두어로 구분). 같은 행사에 재예보가 진행 중이면 409(`reforecast_in_progress`).
  - 응답: 계약 `reforecast-result` — `level`·`peakConcurrent`·`dailyMean`은 **두 스냅샷의 forecast 값 그대로**(재계산·반올림 없음), `weather`: 새 예보에 날씨 보정 근거(T-208이 만드는 evidence — 가정·데이터 kind, 기상청 데이터셋)가 있으면 `applied=true`·그 id들, 없으면 `false` + 이유(행사일이 10일 넘게 남음·과거·보정 표본 부족·날씨 없음). 계약 검증 뒤 응답.
