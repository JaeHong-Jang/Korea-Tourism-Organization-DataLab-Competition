- 인터페이스:
  - **분류**: 키워드 규칙 먼저 — 방문객("가고 싶", "갈 만한", "추천", "어디", "구경", "놀러", "이번 주말", "데이트") → recommend, 주최자("열어요", "준비", "개최", "주최", "해요"+일시·장소) → 새 예보. 애매하면 LLM 한 번(상한 안), 그래도 애매하면 되묻기 버튼 두 개("행사를 여는 쪽이에요" / "가 볼 행사를 찾아요").
  - **recommend 플레이북**: 문장에서 조건 — 유형(불꽃·공연·꽃·먹거리·전통·대학), 지역(시도·시군구 이름 사전 — 일괄 예보의 `sigunguName`·시도), 기간("이번 주말"·"다음 주"·"10월"·"추석" 등 한국 날짜 표현 → KST 날짜 범위, 없으면 오늘~30일) — 을 뽑고, 일괄 예보(`/v1/festivals/upcoming`)에서 걸러 정렬(기본 가까운 날짜, "덜 붐비는/한적한" → 순간 최대 p50 작은 순, "큰/유명한" → 큰 순), 최대 10개를 `recommend` 이벤트로(숫자는 summary 그대로, `reason`은 조건 일치만), `done.forecastId = null`. 결과 0개면 조건을 넓혀 한 번 더(기간 60일) → 그래도 0이면 `recommend` 빈 목록 + 안내 `note`.
  - **eventId 시작**: 메시지에 `eventId`가 있으면 forecast `GET /v1/festivals/upcoming/{eventId}/event`(새 — 일괄 예보가 쓴 행사 입력 그대로, 없으면 404 → `error`)로 행사를 받아 **추출·장소 되묻기 없이** 새 예보(평시·유사 적재 → 예보관 → A → 보고팀 → B → 발행, `new` 모드 — 재예보 흐름과 같은 함수 재사용). 행사 카드(`event_card`)는 그 입력으로 한 번.
  - **중계**: `/api/images/{eventId}`(forecast 프록시, 바이트·Content-Type 그대로, 404 그대로), `/api/evidence/graph`(knowledge `/v1/master/graph` 프록시, 계약 검증).
