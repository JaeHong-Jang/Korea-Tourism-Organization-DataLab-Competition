## 게이트 피드백 1회차 (워커 BLOCKED → 오케스트레이터 결정 — 계약 dccd7ff) — 워크트리 변경 없음
막힌 세 가지(스냅샷 밖 문장 거부·작성자 검증·날짜 숫자)를 **"계획서 담당은 새 문장을 쓰지 않는다"**로 한 번에 푼다. 위 인터페이스 중 "섹션 문장(`plan-templates.ts`)·검증·발행" 부분은 이 결정으로 **대체**한다:
1. **섹션 = 스냅샷의 발행 문장 배치**: records에 저장된 최초 예보서 스냅샷(`session.published.report` = records `GET /v1/snapshots/{forecastId}`와 같은 것)의 `published` 문장만 섹션에 넣는다(T-504 규칙 그대로 통과). 배치 규칙(결정적): `overview` ← 판정 문장 + 참고용·미검증 고지, `crowd-timeline` ← 수치 문장(+ 시간대 자료가 없으면 `검토 필요`), `routes-evacuation`·`traffic-parking`·`medical-toilets` ← 주제 키워드가 맞는 권고 문장(없으면 `검토 필요`), `non-crowd-risks` ← 나머지 권고 문장·위험 요소 판정, `staffing`·`organization`·`weather-emergency` ← `검토 필요`(T-306b·T-210). 한 문장은 한 섹션에만. 후속 why 문장(스냅샷에 없음)은 쓰지 않는다. 행사 일시·장소는 docx 요약 표(T-504)가 보여 주므로 문장을 만들지 않는다.
2. **검증·발행 없음**: 새 문장이 없으므로 게이트 B·발행을 하지 않는다(이미 검증·발행된 문장뿐). `source-check`·`number-check` 수정 불필요.
3. **계획 id**: `plan-${forecastId에서 "f-"를 뺀 값}`(결정적 — 같은 예보 = 같은 계획, 두 번째 요청은 409 → `GET /v1/plans/{id}`로 기존 것).
4. **스트림(계약 dccd7ff — R6 예외)**: `agent_status`/`agent_step`(lead·plan-writer — note 예: "초안 9섹션 중 5섹션을 발행 문장으로 채웠어요, 4섹션은 검토 필요") → `suggest{actions:[{id:"plan-docx", label:"계획 초안 docx 받기", href:"/api/plans/{planId}/export.docx"}]}`(action의 새 선택 필드 `href`) → `done{forecastId=기존 예보}`. 문장·근거·게이트 이벤트는 없다. 계약 픽스처 `fixtures-sse/valid-followup-draft-link.json`과 같은 모양, `sequenceProblems(events, {mode:"followup", forecastId})` 통과.
5. **게이트웨이 프록시**(`routes/plans.ts`): `GET /api/plans/{id}`(계약 `plan` 검증)·`GET /api/plans/{id}/export.docx`(바이너리 그대로, Content-Type·Content-Disposition 유지) → records.
- 수용 기준(갱신): 위 배치 규칙 단위 테스트(주제 키워드·한 문장 한 섹션·`검토 필요` 이유), 가짜 records가 T-504 규칙(스냅샷 발행 문장만·body = rendered 연결·9섹션 순서)으로 확인, 두 번째 요청 = 같은 계획, records 422 → 오류 안내, 발행 전 → 안내(T-305 그대로), 프록시 두 경로(docx 바이트·헤더 그대로), followup 순서 규칙. 실사용(docx를 열어 9섹션·각주 확인)은 오케스트레이터.
